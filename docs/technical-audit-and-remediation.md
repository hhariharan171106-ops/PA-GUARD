## Backend failures fixed

The initial full run had four failures. The fixes were:

1. Evidence rationale generation now returns an existing deterministic explanation for invalid policy findings rather than replacing it with an LLM explanation; missing explanations can still use the local explainer.
2. Case resource-scope authorization now runs before route-role authorization. Out-of-scope cases return 404; an in-scope case with an unauthorized role returns 403.
3. Approval API test fixture now models the recommendation and operational tables/columns required by approval detail responses.
4. Document correction regression test now supplies the required administrative reason. The recovery test also asserts that unavailable SLA ML is reported as unavailable while deterministic operational urgency remains available.

## SLA behavior and limitations

- `sla_deterministic_risk.py` calculates actual operational status from deadline, SLA settings, unresolved documents, workflow failures, follow-ups, assignment, and terminal case status. The operational endpoint and case details view show this independently of prospective probability.
- The prospective SLA endpoint rejects cases outside its prediction domain (including resolved or already-overdue cases); workflow can still return the deterministic operational assessment with an explicit unavailable ML state when the model is unavailable.
- The serving v2 model path remains separate from v3 experimental artifacts. Evaluation uses a fixed seed, 60/20/20 stratified train/validation/test split, train-only preprocessing, validation-only threshold selection, and a sealed test set. The tested target is generated from a synthetic resolution-time simulator. `hours_remaining` has a strong relationship to that target by definition, so metrics do not establish real-world performance or temporal generalization.
- The audit run used 6,000 simulated cases (seed 20261018), 3,600/1,200/1,200 train/validation/test rows, and generated a separate experimental artifact and reports. At the validation-selected threshold 0.47284682, the sealed synthetic test yielded breach precision 0.9315, recall 0.9630, ROC-AUC 0.9719, PR-AUC 0.9914, and Brier score 0.0598. These measure simulator agreement only. See `backend/reports/audit_20261024_sla_eval.json` and `.md`.

## Evidence behavior and limitations

- Deterministic policy validation and experimental document-gap prediction are separate outputs. Requirement results retain SATISFIED, MISSING, UNCERTAIN, and CONFLICTING states; clinical satisfaction requires human review. ML predictions cannot upgrade a deterministic requirement status.
- Missing model artifacts result in an explicit unavailable prediction; they do not create a clinical finding. Policy-specific categories and requirements are exposed with validation results.
- The reproducible Eka run used 288 images across only Lab-report (218) and Prescription (70), with a seeded 216/72 split and no duplicate MD5s. The classifier reached 52.78% accuracy versus 76.39% for the majority baseline; macro F1 was 0.4688 versus 0.4331. This dataset has no prior-authorization necessity or evidence-sufficiency labels. The isolated report is `backend/reports/audit_20261024_eka/eka_document_classification_evaluation.json` and `.md`.

## Policy provenance finding

The existing CMS example asserted public verification without adequate source provenance and its checklist content was not substantiated by the referenced National Coverage Determination. It is retained as unapproved demo data. The migration forces `MOCK_DEMO`, `approved=0`, normalizes the cited source-version date to 2018-04-10, and clears verification metadata while preserving its checklist for demonstration/audit. A manager/admin verification action now requires source location and supporting excerpt for every stored requirement, and the known EVD-CMS-MRI v1.0 / NCD 220.2 pairing is explicitly refused. Requirement creation/update cannot self-assign public verification; draft edits clear verification evidence.

Policy selection requires approval, matching payer and service scope, and current effective/expiry dates. Unsubstantiated public metadata is rejected. Approved fictional examples remain usable in `DEMO_ONLY` mode and the finding/UI explicitly state that they are not authoritative payer guidance. If no suitable approved policy exists, the result is `UNAVAILABLE` with `NEEDS_REVIEW`, empty requirements, and no evidence validations. The case-edit guard also excludes public rows missing verification metadata.

The source reviewed was CMS [NCD 220.2, Magnetic Resonance Imaging](https://www.cms.gov/medicare-coverage-database/view/ncd.aspx?NCDId=177), with version effective date 2018-04-10. The source does not substantiate the prototype's stored neurological-deficit/conservative-therapy checklist. The live row is `policy_documents.id=13`, `EVD-CMS-MRI` v1.0, `CMS Medicare` / `Lumbar MRI`; it remains in the database with its two demo requirements, `MOCK_DEMO`, `approved=0`, `effective_date=2018-04-10`, and cleared source-verification fields. The source URL is retained only as a citation, not as verification. Existing proprietary payer examples remain demo/unverified until independently reviewed. This verification flow is CMS-specific and is not a general-purpose authoritative-source registry. Requirement excerpts are captured as human-review evidence; the server does not fetch CMS text or independently establish quote authenticity, so the policy remains unverified and the known mismatch is explicitly refused.

## Ollama explanation latency correction (2026-10-24)

- Investigation evidence: saved `workflow_failures` rows for `PA-1048` and `PA-1049` report the configured 90-second Ollama timeout. The previous generation path used blocking `urllib.request.urlopen` with no keep-alive and a 90-second timeout. The case workflow invoked several agent explanation stages serially and then invoked another workflow summary generation. At inspection, `OLLAMA_MODEL` resolved to `qwen3.5:latest` (local listing: 6.6 GB), while `ollama ps` showed no loaded process. Existing records contain no phase telemetry, so those timeouts cannot distinguish model loading from inference; no single internal cause is claimed.
- Case analysis now returns the deterministic operational explanation immediately with distinct experimental SLA probability, rule-based operational risk/reasons, document verification count, evidence review state, escalation threshold state, and next action. It retains the synthetic/unvalidated disclaimer and makes no clinical determination. Evidence-agent OCR/ML wording calls are suppressed only inside this whole-case workflow, preventing redundant sequential model calls; standalone agent endpoints are unchanged.
- Ollama enhancement is explicitly user-requested and asynchronous through case-scoped start/status routes. It uses one bounded in-flight request, a reusable async HTTP client, bounded connect/read/write/pool timeouts, compact structured prompts, and a short keep-alive. The configured default generation timeout is now 30 seconds, clamped to 5–60 seconds. Errors return `UNAVAILABLE` while the deterministic explanation remains available; the UI offers a retry without rerunning the workflow. Same-input requests deduplicate, successful results cache for ten minutes, and the fingerprint rejects results when the case, document/review, assignment, escalation, SLA configuration, or applicable payer/service policy inputs change. No retry is performed automatically.
- Logs/audit telemetry include a correlation ID, model, elapsed time, available load/token counts, failure category, retry/cache outcome, and fallback status. Prompts, OCR text, patient identifiers, and case IDs are not logged. Ollama response duration fields are recorded when present; the original historical timeout rows remain unchanged.

## Manager approval queue state correction (2026-10-24)

- Confirmed root cause: `/api/approvals` constrained Specialist and Supervisor queues by workflow state, but the Manager's default queue only excluded final `APPROVED` and `DENIED` cases. Thus a `NEW` case could appear in the Manager's pending list even though `/api/approvals/{case_id}/action` correctly rejects Manager `APPROVED` from `NEW`. This is a queue eligibility/query defect, not a missing Supervisor handoff update or a stale action value.
- The existing handoff transitions were confirmed: Specialist `SUBMIT` changes `NEW`/specialist review to `AWAITING_SUPERVISOR`; Supervisor `FORWARD`, or `SUPERVISOR_APPROVE` when manager-final review is configured, changes `AWAITING_SUPERVISOR` to `AWAITING_MANAGER` and assigns a Manager. `pa_reviews`, `pa_assignment_history`, and audit events persist the acting user, reason, from/to state, and timestamp. The Manager action endpoint already permits decisions from `AWAITING_MANAGER` and manager-retained `UNDER_REVIEW` only.
- Manager default and non-final filtered queues now include only `AWAITING_MANAGER` and `UNDER_REVIEW`; explicit `APPROVED`/`DENIED` historical queries remain available. The backend continues to reject direct approval from `NEW`. The Manager UI presents decision buttons only in the two eligible states and explains when a case has not been handed off.
- Approval reasons are trimmed and whitespace-only values are rejected. Status-action audit detail now records structured reason, previous state, and resulting state in the same transaction as the case update and `pa_reviews` entry. Manager approval/return, return-to-Supervisor, and duplicate finalized actions are covered by isolated API tests. The existing Supervisor handoff also has an end-to-end queue-state/reason/assignment-history regression test.
